
## **클린 코드 4장 요약 – 주석(Comments)**

> *“나쁜 코드에 주석을 달지 마라. 새로 짜라.”*
> — 로버트 C. 마틴

---

### 1. **주석의 역할과 한계**

#### (1) 코드의 목적을 설명하는 도구

주석은 코드의 의도나 설계 의도를 설명하기 위해 사용된다. 하지만 주석은 본질적으로 **코드 품질이 낮을 때 보완하는 수단**일 뿐이다. 잘 짜인 코드는 주석 없이도 읽는 사람이 **“무엇을, 왜 하는지”**를 자연스럽게 이해할 수 있어야 한다.
주석은 일종의 **“코드 냄새(Code Smell)”**로, 코드가 명확하지 않다는 신호일 수도 있다.

#### (2) 주석의 진실성과 유지 비용

주석의 가장 큰 문제는 **“시간이 지나면 거짓말을 한다”**는 점이다.
코드는 계속 수정되지만 주석은 종종 방치된다. 그 결과, 오래된 주석은 오히려 잘못된 정보를 주어 혼란을 초래한다.
즉, **잘못된 주석은 없는 것보다 더 해롭다.**

---

### 2. **좋은 주석과 나쁜 주석의 구분**

#### (1) 좋은 주석의 특징

좋은 주석은 **코드로 표현할 수 없는 부가 정보를 제공**한다.
예를 들어 다음과 같은 경우는 주석이 유용하다.

* **법적, 규제적 요구사항**

  ```java
  // Copyright (C) 2025 IBK. All rights reserved.
  ```

  라이선스, 저작권, 감사기록 등은 반드시 주석으로 명시해야 한다.

* **의도와 이유를 설명하는 주석**

  ```java
  // 성능 최적화를 위해 캐시를 사용하지 않음
  ```

  “무엇을 하는가”가 아니라 **“왜 그렇게 하는가”**를 설명할 때 주석이 유용하다.

* **경고나 중요 정보**

  ```java
  // NOTE: 이 함수는 멀티스레드 환경에서 호출되지 않아야 함
  ```

  시스템적 제약이나 위험 요소를 명확히 하는 용도로 사용한다.

* **TODO, FIXME 주석**
  개선 예정이거나 버그가 있는 부분을 명시적으로 표시한다.
  단, 일정 기간 내 해결되지 않는 TODO는 기술 부채가 된다.

#### (2) 나쁜 주석의 특징

나쁜 주석은 **코드의 복잡함을 감추기 위한 핑계**다.

* **코드 자체를 설명하는 주석**

  ```java
  // i에 1을 더한다
  i++;
  ```

  코드를 그대로 반복하는 주석은 불필요하다.

* **오해를 유발하는 주석**
  잘못된 정보, 오래된 설명, 부정확한 예시는 혼란을 초래한다.

* **주석으로 문제를 덮는 경우**
  복잡하거나 잘못된 로직을 “임시로 설명”하는 주석은 근본적인 해결이 아니다.
  주석 대신 **리팩터링(refactoring)**이 필요하다.

---

### 3. **좋은 코드는 주석 없이도 읽힌다**

#### (1) 주석 대신 코드로 의도를 표현하라

좋은 네이밍과 구조화된 함수가 주석보다 훨씬 강력하다.
예를 들어:

```java
// bad
// 고객이 골드회원인지 확인
if (cust.age > 29 && cust.totalPurchase > 1000000) ...

// good
if (customer.isGoldMember()) ...
```

이처럼 의미 있는 함수명, 변수명, 클래스명은 주석을 대체할 수 있다.

#### (2) 코드 정리로 주석을 제거하라

주석을 추가하기 전에 스스로에게 질문해야 한다.

> “이 주석 없이도 의도를 드러낼 수 있는가?”
> “함수 이름이나 구조를 바꾸면 더 명확해질 수 있는가?”

대부분의 경우, **함수 분리, 변수명 개선, 조건식 단순화**로 주석을 없앨 수 있다.
주석보다 리팩터링이 우선이다.

---

### 4. **주석이 필요한 예외적인 상황**

#### (1) 외부 환경이나 정책적 이유

API 호출 시 제한사항, 타 시스템의 오류 회피 로직 등 **코드 외부 요인**에 대한 설명은 주석이 필요하다.
예:

```java
// 외부 결제 시스템 버그로 인해, 0 금액 결제 요청은 차단함.
```

#### (2) 복잡한 수학적 계산, 알고리즘의 근거

논문에 기반한 수학 공식이나 특정 알고리즘 로직은 코드만으로는 완벽히 설명하기 어렵다.
이 경우, **출처나 계산 근거**를 간단히 남기는 것이 좋다.

#### (3) 변경 이력 주석 (단, 버전 관리 시스템이 없는 경우)

Git과 같은 형상관리 시스템이 없다면, 중요한 변경의 이유를 남기는 주석은 가치 있다.
다만, 현대 개발환경에서는 Git log나 commit message가 이를 대신한다.

---

### 5. **주석 작성의 원칙**

#### (1) 코드보다 먼저 쓰지 말 것

주석은 코드 완성 후 필요한 경우에만 추가한다.
코드를 작성하기 전 계획 주석(예: “여기서 DB 연결할 것”)은 대부분 잊혀진다.

#### (2) 정확하고 간결하게 쓸 것

주석은 한 문장으로 **“무엇을, 왜”**를 명확히 전달해야 한다.
추상적이거나 장황한 주석은 도움이 되지 않는다.

#### (3) 포맷과 규칙을 통일할 것

* `// TODO:` : 개선 예정
* `// FIXME:` : 오류 수정 필요
* `// NOTE:` : 주의사항
  이와 같은 통일된 주석 규칙은 팀 협업에서 큰 도움이 된다.

---

### 6. **주석보다 리팩터링을 우선하라**

주석이 많다는 것은 코드가 명확하지 않다는 증거다.
주석을 달기 전에 다음을 시도해야 한다.

| 개선 목표  | 방법              |
| ------ | --------------- |
| 의도 명확화 | 함수·변수명 개선       |
| 로직 단순화 | 조건식 분리, 메서드 추출  |
| 가독성 향상 | 일관된 들여쓰기, 공백 사용 |
| 중복 제거  | 공통 로직 메서드화      |

주석 없이도 “읽히는 코드”를 만드는 것이 클린 코드의 핵심이다.

---

### 7. **요약 및 교훈**

* **주석은 최후의 수단이다.**
  → 코드로 의도를 표현할 수 없다면, 그때만 주석을 고려하라.

* **주석은 코드와 함께 유지되어야 한다.**
  → 주석이 오래되면 진실을 왜곡한다. 항상 최신 상태로 관리하라.

* **주석 대신 리팩터링하라.**
  → 주석이 많아질수록 코드가 불명확하다는 신호다.

* **좋은 주석은 “왜(why)”를 설명한다.**
  → “무엇(what)”은 코드가, “왜(why)”는 주석이 말한다.

---

## **결론**

> **“좋은 코드는 주석이 필요 없다.
> 주석이 필요하다면, 그 이유를 먼저 의심하라.”**

로버트 C. 마틴은 주석을 코드 품질의 보완재가 아닌,
**명확한 코드의 대체물이 되어선 안 된다**고 강조한다.
따라서 개발자는 주석을 남기기 전에
**함수명, 변수명, 구조를 개선하여 코드 자체로 의도를 표현할 수 있는가**를 스스로 점검해야 한다.

주석은 “코드의 설명서”가 아니라,
“코드가 말하지 못하는 마지막 단어”일 뿐이다.
