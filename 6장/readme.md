# 클린 코드 6장 – 객체와 자료 구조

----------

### 1. **개요: 객체와 자료 구조의 대립**

로버트 C. 마틴은 “객체는 추상화로 내부를 숨기고, 자료 구조는 내부를 노출한다”고 설명한다. 객체는 **행동(메서드)** 중심으로, 자료 구조는 **데이터(필드)** 중심으로 설계된다. 이 두 개념은 서로 반대되는 방향의 사고방식을 요구한다. 좋은 설계자는 두 개념의 차이를 이해하고 상황에 맞게 선택해야 한다.

----------

### 2. **객체지향의 핵심 – 구현 숨기기**

객체의 목적은 **데이터를 감추고 인터페이스를 통해서만 조작하도록 하는 것**이다.  
즉, 외부에서는 객체의 내부 구조를 몰라도 동작을 예측할 수 있어야 한다. 이를 통해 변경이 발생하더라도 외부 코드의 영향을 최소화할 수 있다. 반면, 내부 데이터를 노출하면 외부 코드가 의존성을 갖게 되어 수정 시 파급효과가 커진다.

----------

### 3. **자료 구조의 목적 – 데이터 접근성**

자료 구조는 데이터를 숨기지 않고, **데이터를 효율적으로 전달·처리**하는 것이 목표다.  
함수나 모듈이 자료 구조를 다룰 때는 데이터 필드에 직접 접근하여 조작할 수 있다. 대표적으로 DTO(Data Transfer Object)나 VO(Value Object)처럼 단순한 자료 전달용 구조체는 행동보다 데이터 표현이 중요하다.

----------

### 4. **객체 vs. 자료 구조의 사용 기준**

-   **객체 사용**: 시스템의 행위 중심, 변경 가능성이 높은 로직이 존재할 때.
    
-   **자료 구조 사용**: 계산이나 변환 로직이 명확하고 데이터 중심일 때.  
    두 방식을 혼합하면 혼란스러운 구조(절반은 캡슐화, 절반은 노출)가 되어 유지보수가 어렵다. 따라서 **하나의 모듈은 일관된 접근 방식을 가져야 한다.**
    

----------

### 5. **절차적 코드와 객체지향 코드의 트레이드오프**

-   절차적 코드는 새로운 자료 구조를 추가하기 쉽지만, 새로운 동작을 추가하기 어렵다.
    
-   객체지향 코드는 새로운 동작을 추가하기 쉽지만, 새로운 자료 구조를 추가하기 어렵다.  
    따라서 시스템의 확장 방향(행위 중심 vs. 데이터 중심)에 따라 적합한 구조를 선택해야 한다.
    

----------

### 6. **디미터 법칙과 자료 노출 금지**

디미터 법칙(Law of Demeter)은 “객체는 자신의 바로 이웃 객체와만 상호작용해야 한다”고 말한다.  
객체가 내부 구조를 드러내거나 체이닝으로 접근하게 되면 캡슐화가 깨진다. “a.getB().getC().doSomething()” 같은 코드는 나쁜 예다. 이런 설계는 **자료 구조처럼 행동하는 객체**로, 양쪽의 장점을 모두 잃는다.

----------

### 7. **결론: 구분의 지혜**

좋은 설계자는 **객체와 자료 구조를 명확히 구분**하고, 시스템의 성격에 따라 적절히 사용한다.  
즉, 변경 가능성과 유지보수성을 고려하여 **행동 중심(객체지향)** 또는 **데이터 중심(절차적 구조)** 중 하나를 선택하는 것이 핵심이다.  
캡슐화를 지키고, 인터페이스 설계를 통해 의존성을 줄이는 것이 ‘깨끗한 코드’의 본질이다.
